# 维护手册

维护的目标不是「让库看起来干净」，而是**让输入继续流动、让判断继续更新**。

## 每周 30 分钟

固定一个时间，按顺序做，不跳步。

| 分钟 | 动作 | 完成判据 |
|---|---|---|
| 0–5 | 看 [[知识库主页]] 的收件箱 | `A 临时想法` 里值得留的移入 D，其余删除 |
| 5–15 | 从消化队列挑**一篇** | 读完 → 02 写三行转述，或直接归位到 03/04 |
| 15–20 | 看进行中的项目 | 每个项目写下一个具体下一步；没有下一步的改 `暂停` |
| 20–25 | 看需复习队列 | 只处理最旧的一篇：补证据或降级 |
| 25–30 | 写 [[_模板_每周回顾]] | 输入、判断变化、输出、下周一件事 |

**一次只处理一篇。** 不要试图清空队列；清空是症状，不是目标。

## 每月 2 小时

1. **归档**：把已完成的项目、被取代的主题笔记移入 `99 归档`，`status` 改 `已归档`。
2. **跑审计**：`python3 tools/kb_audit.py`。先修 FAIL，再决定 WARN 要不要处理。
3. **复习队列**：把所有 `需复习` 过一遍。结论仍成立 → 补新素材并推进 `evidence_as_of`；被推翻 → 降级或归档。**不得只改 status。**
4. **标签收敛**：搜索只用过一次的标签，合并同义词或删除。
5. **备份**：`git add -A && git commit`。没有 git 就复制整个库到外部存储。
6. **模板复盘**：这个月有没有哪次新建笔记后大量手改 frontmatter？有的话改模板。

## 空队列是警报

工作台的四个查询块长期为空，含义是：

- 收件箱空：这周没有新输入
- 消化队列空：没有在读、在想的东西
- 项目空：没有正在推进的事
- 需复习空：要么真的都新，要么从来没用过这个状态

**正确反应是去读、去聊、去动手，不是批量改 status 让数字好看。**

这条规则来自一个真实的失败：一个治理到零缺陷的知识库，连续 75 天没有一条新捕获，却还在不断增加审计维度。**尺子越多，不代表水在流。**

## 状态诚实

- 项目 `进行中` 的判据是**过去 30 天有真实动作**，不是主页写得完整。
- 04 的 `已沉淀` 判据是**作者确认这个判断仍然成立**，不是格式填完了；02 的 `已沉淀` 只表示来源已消化完。
- 含未确认推断的 04 卡用 `草稿`，不要用 `已沉淀`。
- `endorsed` 只能由作者填。AI 代填等于把生成内容伪装成你的判断。

## 批量修改前

1. 先备份：git commit，或复制到 `.backup/YYYY-MM-DD/`。
2. 先 Grep 同类问题，确认影响范围。
3. 一次只改一类字段（例如只改 status，不顺手改 tags）。
4. 改完跑审计，确认没有新增 FAIL。
5. 未跟踪的文件（`git status` 显示 `??`）删掉就没了，先复制再删。

## 改模板

- 只改 `07 资料库/D 模板/` 里的权威模板。
- 模板里的 `status` 是**新建笔记的初始状态**，不是模板自己的状态。
- 改完同步 `tools/kb_config.json` 与 [[模板库]] 的表格。
- 跑一次审计，确认模板目录仍被跳过。

## 不要做的事

- 不要为了「体系完整」新增目录、字段、查询块。先问：现在的痛点是什么？
- 不要在没有输入的时候扩治理。治理不产生内容。
- 不要删除唯一副本。归档是可逆的，删除不是。
- 不要用「主页很久没更新」判断项目死了，也不要用「主页很完整」判断项目活着。
- 不要为了清队列改状态。

## 什么时候该升级

如果你已经连续 30 天有捕获、积累了 5 张以上常青卡，并且开始觉得 Lite 不够用，再看 [[升级路线]]。**没到触发条件就不要加。**
