# 设计取舍

这不是唯一正确的知识库形状。它是针对一个特定阶段做的取舍：**个人使用、中文、刚刚开始、最缺的是持续输入而不是更多结构。**

> 本文的「Lite 版」即 README 里的 Starter v0.1。

下面每一条都来自一个真实知识库踩过的坑。为方便分享，不引用具体私人内容。

## 1. 先闭环，后覆盖

**源库的教训**：一个 240+ 篇（复盘时点；原库后来继续增长）、治理到机械层零缺陷的知识库，连续 75 天没有一条新捕获。它有 27 个模板、440 行协作契约、十几套审计维度，但输入断流。

**这里的选择**：8 个顶层目录、7 个模板、约 140 行协作契约。先让「捕获 → 消化 → 判断 → 输出」跑通，再谈覆盖。

**代价**：没有长期领域、没有发布流水线、没有项目组合的高级视图。这些都在 [[升级路线]] 里，等触发条件到了再加。

## 2. 文件夹表示流程位置，不表示主题

**源库的教训**：按主题分目录会让「一篇笔记属于哪个主题」变成建笔记时最难的决策，也会让跨主题的判断无处安放。

**这里的选择**：02 是来源消化，03 是判断，04 是原子知识。主题靠标签和双链表达。

**代价**：不能靠点文件夹浏览某个主题的全部内容，需要用标签面板或搜索。对个人库，这个代价很小。

## 3. 三层严格分工，只链接不复制

**源库的教训**：同一段原文在 02、03、04 各存一份，改一处就要改三处，最后三处说法不一致。

**这里的选择**：
- 02 只放来源消化
- 03 写判断与因果链，证据层只放 `[[02#锚点]]`
- 04 只放能独立成立的一句话判断

**代价**：03 必须能脱离 02 读懂；写 03 比复制粘贴费力。但这是「形成自己的判断」必须付的成本。

## 4. 模板是「实例种子」，不是「模板笔记」

**源库的教训**：27 个模板全部写 `status: active`。用它们新建的笔记一开始就是非法状态：主题笔记应该是 `已提炼`，常青卡应该是 `已沉淀`，项目应该是 `进行中`。于是每篇新笔记都要手动改 status，或者干脆不改，让词表失真。

**这里的选择**：模板里写**目标实例**的 `type` 与初始 `status`；模板目录整体豁免审计。

**代价**：模板文件本身不再是一篇「有生命周期的笔记」。这是正确的：模板是种子，不是内容。

## 5. 文件名全库唯一

**源库的教训**：14 个文件都叫「项目主页」。Obsidian 的 `[[项目主页]]` 会静默跳到其中一个，不报错。为了安全，所有链接都必须写顶层全路径，写链接变成负担。

**这里的选择**：项目主页叫 `<项目名>-项目主页.md`，目录说明叫 `<目录名>说明.md`。唯一文件名可以用最短的 `[[文件名]]`，移动目录也不会断。

**代价**：文件名更长，需要命名纪律。比每次写全路径便宜。

## 6. 状态必须诚实，允许「草稿」

**源库的教训**：`已沉淀` 被当成「格式填完了」的印章。正文明明写着「本节为草稿，待用户确认」，status 却是 `已沉淀`。词表里没有「内容成形但作者没确认」这个状态。

**这里的选择**：04 增加 `草稿`；`已沉淀` 只用于作者确认过的判断；可选的 `endorsed` 记录确认日期，AI 不得代填。

**代价**：多了一个需要判断的状态，不能靠「填完模板」自动升级。这正是它有意义的原因。

## 7. 审计是证伪工具，不是评分

**源库的教训**：机械指标全绿，但覆盖率只有 28%，复习队列 9 篇从未收口。零缺陷给人一种「库很健康」的错觉。

**这里的选择**：审计只报三类结果——FAIL（结构违约）、WARN（值得看，不一定是错）、PASS。覆盖率、陈旧度只做 WARN，不追求清零。审计明确写出「不检查什么」。

**代价**：没有单一的「健康分」。你需要读 WARN 并做判断。

## 8. 配置驱动，标准库实现

**源库的教训**：审计脚本硬编码路径和基准日，放在不被版本控制的目录里；换一台机器或过一个月，结论就失真。

**这里的选择**：`tools/kb_config.json` 集中所有词表与路径；Python 只用标准库；脚本进版本库；关键解析逻辑有单元测试。

**代价**：JSON 不能写注释，不如 YAML 好看；配置和文档需要手动同步（[[受控词表]] 已写明这一点）。

## 9. 零插件依赖

**源库的教训**：工作台的查询块曾因语法错误长期失效；一旦依赖 Dataview，换设备或插件升级就可能全黑。

**这里的选择**：只用 Obsidian 原生嵌入搜索，frontmatter 过滤写成 `[status:值]`；不安装任何社区插件。

**代价**：原生查询的表达力有限，做不了复杂的聚合和排序。个人库的前四个视图够用。

## 10. 治理冻结，输入优先

**源库的教训**：近 30 天新增内容里，治理文档占了很大比例，而作者的新想法只有几十行。每轮维护都能发现新的「尺子问题」，但流量数字一个没变。

**这里的选择**：Lite 版不设维护日志、不设覆盖率矩阵、不设多套审计报告。规则够用就停。**发现新问题时，先问它是否影响今天的捕获或判断；不影响就记下来，不马上加规则。**

**代价**：一些真实的小问题会被暂时容忍。这是刻意的：结构洁癖会挤占输入的时间。

## 我们故意没做的

| 没做 | 原因 |
|---|---|
| 27 个细分模板 | 7 个覆盖 90% 场景；模板越多，选择成本越高 |
| 440 行协作契约 | 初始化预算被规则吃掉，AI 反而读不完 |
| 小节级覆盖率矩阵 | 对个人库是过度测量；先有判断，再谈覆盖 |
| 每日 20 篇批量摘要 | 收藏不等于消化；批量输入会制造虚假的充实感 |
| 发布平台流水线 | 第一次输出之前，流水线是空转 |
| `06 长期领域` | 先用项目跑起来；年度目标等有真实节奏再加 |
| 一百多个标签 | 标签是检索工具，不是分类展览 |
| HTML 仪表盘 | 原生查询够用；仪表盘会变成新的维护对象 |
| AI 自动补全双链 | 会产生大量看似合理、实际错误的关联 |

## 这些取舍的代价

- Lite 版不能管理年度目标、长期责任和发布流水线。
- 示例内容需要清理一次（可脚本或手动）。
- 唯一文件名需要持续自律。
- 审计不检查外部链接是否存活、附件是否存在、内容是否准确。
- 没有覆盖率矩阵，你无法一眼看到「读了多少、转化了多少」。

如果你能接受这些代价，并且最需要的是**开始持续输入**，这套结构就是合适的。如果你已经有稳定的输入和大量卡片，直接看 [[升级路线]]。

## 什么时候该推翻这些取舍

- 连续 30 天有捕获，且开始需要年度目标 → 加 `06 长期领域`
- 常青卡超过 30 张，开始找不到 → 加合集或更强的索引
- 原生查询不够用 → 再考虑 Dataview / Bases
- 多人协作 → 这套「个人判断库」的假设不再成立，需要另一套权限与评审结构

**结构应该追着痛点走，而不是跑在痛点前面。**
